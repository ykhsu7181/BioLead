# ScholarLead Agent 项目开发计划书

版本：v0.2  
日期：2026-08-17

## 1. 项目目标

ScholarLead Agent 是面向海外科研服务市场的科研客户线索发现系统。系统围绕公开科研数据，完成从关键词检索、论文/基金/机构数据采集、客户线索清洗、评分分级、邮件草稿生成、人工审核、导出和跟进记录的业务闭环。

主流程：

```text
关键词或自然语言输入
→ 创建检索任务
→ 多数据源采集
→ 保存原始数据
→ 数据清洗与结构化
→ PI/客户线索生成
→ 评分分级
→ 邮件草稿生成
→ 人工审核与发送
→ 导出与报告
```

## 3. 技术架构建议

建议采用分层模块，而不是一个大 Agent。

```text
collectors/       数据源采集
parsers/          原始响应解析
cleaning/         DOI、日期、姓名、机构、邮箱清洗
matching/         PI/客户归并与人工确认候选
scoring/          四维评分和解释
ai/               邮件草稿、客户分析、Token 记录
email/            邮件草稿、审核、发送、日志
reports/          CSV/Excel/客户报告/任务报告
database/         SQLite schema 和数据访问
```

## 4. 核心数据模型

第一版建议使用 SQLite，主要表包括：

- `search_tasks`：检索任务。
- `raw_records`：原始响应记录。
- `papers`：论文和预印本。
- `authors`：作者。
- `institutions`：机构。
- `grants`：基金。
- `contacts`：邮箱和来源。
- `leads`：客户线索。
- `lead_scores`：评分结果。
- `email_drafts`：邮件草稿。
- `email_send_logs`：邮件发送记录。
- `exports`：导出记录。
- `operation_logs`：操作日志。
- `ai_usage_logs`：模型调用和 Token 费用。
- `settings`：评分权重、阈值、关键词、模板、模型配置。

## 5. 阶段计划

### 阶段 0：计划确认

交付：

- 项目开发计划书。
- 数据源可行性说明。
- 功能完成度与验收矩阵。
- PubMed 第一轮主链路方案。

目标：

- 明确开发范围。
- 明确受限数据源。
- 明确甲方配合事项。

### 阶段 1：PubMed 单源主链路

交付：

- PubMed ESearch / EFetch。
- 原始 XML/JSON 保存。
- 论文结构化。
- 作者、机构、邮箱解析。
- PI/通讯作者候选线索。
- PubMed 单源临时评分。
- JSON/CSV 导出。

目标：

```text
关键词 → PubMed 采集 → 清洗 → 客户候选线索 → 临时评分 → 导出
```

### 阶段 2：多数据源接入

交付：

- OpenAlex 增强。
- Crossref。
- NIH RePORTER 或 NSF。
- ORCID 或 bioRxiv/medRxiv。
- 多源统一字段结构。

目标：

- 中期前不少于 4 类核心数据源。
- 每条数据保留来源 ID、来源链接或来源标识。

### 阶段 3：客户归并和正式评分

交付：

- PI/客户归并规则。
- 人工确认队列。
- 四维评分。
- 高/中/低优先级。
- 评分依据和推荐理由。

评分维度：

- 资金活跃度 40%。
- 研究方向匹配度 30%。
- 发表时效性 20%。
- 外包倾向 10%。

### 阶段 4：邮件草稿和报告导出

交付：

- 个性化英文邮件草稿。
- 多语言邮件草稿预留。
- 邮件人工编辑。
- 客户列表导出。
- 客户详情报告。
- 任务汇总报告。

### 阶段 5：人工审核发送和后台配置

交付：

- 人工确认后发送邮件。
- 发送状态记录。
- 发件账号和额度管理。
- Token 用量和费用记录。
- 评分权重、阈值、关键词、模板、模型配置。
- 操作日志。

## 6. 甲方配合事项

需要甲方提供或确认：

- 关键词层级表。
- 产品和服务类型表。
- 四维评分规则。
- 低价值线索过滤规则。
- 测试关键词。
- 人工评分样本。
- 客户归并样本。
- 邮件署名和公司服务介绍。

- AI 模型账号/API key。
- 企业邮箱测试账号。
- 是否提供 Web of Science 等付费数据源账号。

## 7. 风险与边界

| 风险 | 说明 | 处理方式 |
| --- | --- | --- |
| 邮箱错配 | 邮箱不一定能准确对应作者 | 必须保留来源，不确定时人工确认 |
| 客户归并错误 | 同名 PI、机构变更、多邮箱会造成误合并 | 强匹配自动合并，弱匹配进入人工确认 |
| 数据源限制 | Google Scholar、ResearchGate 等不稳定 | 不作为自动化核心源 |
| 基金覆盖不足 | 不同国家基金源不同 | 分地区接入 NIH、NSF、CORDIS、KAKEN |
| 邮件合规风险 | 自动群发风险高 | 正式发送必须人工确认 |
| AI 输出不稳定 | 邮件可能模板化或理解偏差 | Prompt 模板化管理，人工审核 |

## 8. 下一步建议

```text
PubMed 采集

→ 结构化清洗
→ 邮箱来源记录

```
