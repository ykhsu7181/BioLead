# PubMed Stage 34A: API Boundary Design

## Goal

Stage 34A defines the first frontend/backend boundary for ScholarLead Agent.
The boundary is intentionally thin: FastAPI exposes existing state and service
entry points, while PubMed, Agent, email, database, and export logic remain in
their current Python modules.

This stage does not replace Streamlit and does not start batch outreach.

## Boundary Rules

- Vue calls FastAPI only.
- Vue must not call PubMed, Crossref, OpenAlex, NIH RePORTER, LLM APIs, SMTP,
  or SQLite directly.
- FastAPI routes must not reimplement PubMed parsing, lead generation, scoring,
  email sending, or result package creation logic.
- Secrets stay server-side. API keys, SMTP credentials, model keys, and `.env`
  values must never be returned to the browser.
- External network behavior stays inside existing clients, services, tools, or
  explicitly approved providers.
- Existing CLI and Streamlit flows remain available for internal validation.

## Response Envelope

All normal API responses use:

```json
{
  "success": true,
  "data": {},
  "error": null,
  "request_id": "..."
}
```

Errors use:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "LEAD_NOT_FOUND",
    "message": "Lead not found"
  },
  "request_id": "..."
}
```

## Current Endpoint Contract

| Method | URL | Purpose |
| --- | --- | --- |
| GET | `/api/health` | API health check |
| POST | `/api/conversations` | Create a conversation shell |
| GET | `/api/conversations/{conversation_id}` | Read conversation metadata |
| POST | `/api/conversations/{conversation_id}/messages` | Append a conversation message |
| GET | `/api/conversations/{conversation_id}/messages` | List conversation messages |
| GET | `/api/tasks/{task_id}` | Read task metadata |
| GET | `/api/tasks/{task_id}/status` | Read task status |
| GET | `/api/tasks/{task_id}/leads` | List leads for a task |
| GET | `/api/leads` | List leads |
| GET | `/api/leads/{lead_id}` | Read one lead |
| GET | `/api/leads/{lead_id}/service-match` | Read stored service-match evidence if available |
| POST | `/api/jobs` | Create a background job record |
| GET | `/api/jobs/{job_id}` | Read a job |
| GET | `/api/jobs/{job_id}/items` | List job items |
| POST | `/api/jobs/{job_id}/retry` | Mark one job item for retry |
| POST | `/api/result-packages` | Reserved result-package creation boundary |
| GET | `/api/result-packages/{package_id}` | Read exported package metadata |
| GET | `/api/result-packages/{package_id}/download` | Download exported package workbook |

`POST /api/result-packages` currently returns a clear not-ready error because
the later application service must create packages from task data without
duplicating export logic in a route.

## Pagination

List endpoints use:

```text
page: integer, default 1
page_size: integer, default 50
```

Responses include:

```json
{
  "items": [],
  "page": 1,
  "page_size": 50,
  "total": 0
}
```

## ID Rules

- `conversation_id`: generated as `conversation-{uuid}` unless supplied.
- `message_id`: generated as `message-{uuid}`.
- `task_id`: created by existing task/run logic.
- `lead_id`: stable lead identifier from the PubMed lead pipeline.
- `job_id`: generated by the background job module.
- `job_item_id`: generated by the background job module.
- `package_id`: result package export identifier.

## Error Codes

| Code | Meaning |
| --- | --- |
| `CONVERSATION_NOT_FOUND` | Conversation does not exist |
| `TASK_NOT_FOUND` | Task does not exist |
| `LEAD_NOT_FOUND` | Lead does not exist |
| `JOB_NOT_FOUND` | Job does not exist |
| `JOB_ITEM_NOT_FOUND` | Job item does not exist or does not belong to the job |
| `INVALID_JOB_REQUEST` | Job creation request failed validation |
| `RESULT_PACKAGE_NOT_FOUND` | Result package metadata or workbook does not exist |
| `RESULT_PACKAGE_CREATE_NOT_READY` | Package creation route exists but waits for later service wiring |
| `INTERNAL_ERROR` | Unexpected server-side error |

## Acceptance

- API boundary and responsibility rules are documented.
- Current core endpoints are listed.
- Response envelope, pagination, IDs, and errors are documented.
- No existing PubMed, Agent, Streamlit, email, or export logic is rewritten.
- Stage 34B and 34C can build on this boundary.
